# Observability

The local collector receives OTLP traces from Go and Python and prints spans to its structured log. Prometheus scrapes the API, the worker and the authenticated capability service. Grafana is an optional local dashboard over that Prometheus; correctness never depends on any telemetry service.

## Trace

The API accepts W3C trace context, opens `http.request`, and for a start opens `workflow.start`, passing the trace parent into the workflow input. Activities restore that context, so one commission is one trace across days:

```
http.request → workflow.start → workflow.run.started → capability.activity → provider.invoke / tool.curated_research
             → persistence.step.save → workflow.revision.created → persistence.revision.save
             → workflow.approval.requested → (human wait) → workflow.decision.recorded → persistence.decision.save
             → artifact.production → persistence.artifact.save → workflow.workflow.completed
```

The `observability` topology phase creates a commission with a known trace id and asserts every span above and unbroken parent linkage in the collector output. Spans carry identifiers and classifications only, never briefs, prompts, tokens or provider bodies.

## Metrics

| Metric | Meaning |
| --- | --- |
| `velin_http_requests_total`, `velin_http_duration_seconds` | API traffic by route pattern and status class; SSE lifetime excluded |
| `velin_workflow_runs_started_total`, `velin_workflow_runs_resumed_total` | Runs recorded; a resumed run is a later attempt of the same commission |
| `velin_workflows_active` | Open executions in Temporal visibility, refreshed every five seconds; use `max` across workers; unavailable queries yield NaN |
| `velin_worker_open_workflows_at_start` | Open executions found on the task queue when the worker started, resumed from history |
| `velin_workflow_outcomes_total{outcome}` | Terminal outcomes: completed, rejected, expired, cancelled, failed |
| `velin_workflow_duration_seconds{outcome}` | Run duration from start to terminal event, including human waits |
| `velin_approval_wait_seconds` | Completed approval wait duration |
| `velin_activity_attempts_total{activity,retry}`, `velin_activity_retries_total`, `velin_activity_failures_total{activity,code}` | Attempts, retries and classified failures |
| `velin_capability_duration_seconds{capability}` | Step duration including the service boundary |
| `velin_artifacts_total` | Artifacts produced |
| `velin_workflow_transitions_total{stage}` | Recorded stage transitions |
| `velin_nats_publish_failures_total`, `velin_progress_hints_published_total` | Disposable hint publication |
| `temporal_workflow_task_execution_failed{failure_reason="NonDeterminismError"}` | Replay failures, from the Temporal SDK metrics bridge |
| `temporal_*` | Every other SDK worker and client metric, projected onto a fixed label set |
| `velin_provider_*`, `velin_capability_seconds`, `velin_schema_failures_total`, `velin_structured_repairs_total`, `velin_tool_failures_total`, `velin_evaluation_checks_total` | Capability service provider attempts, latency, circuit state, repairs, tool outcomes and checks |

Unique workflow counts and task histories remain Temporal visibility and history queries; they are not reconstructed from counters. The SDK creates error series only when an error occurs; a successful replay does not fabricate a replay-failure sample. The topology check verifies real SDK execution/replay latency and application metrics, while the metrics bridge test verifies the non-determinism error labels. No metric is invented for components the system does not use.

## Dashboard

`infra/observability/grafana/velin.json` is generated by `node scripts/grafana-dashboard.mjs` and provisioned read-only under the `observability` Compose profile. It shows outcomes, active runs, duration and approval-wait percentiles, retries, failures, resumed runs, replay failures, artifacts, API and capability latency, provider attempts, circuit state, schema repairs and hint failures.

## Alerting targets

Alert on sustained API 5xx or readiness failure, failed Temporal executions, repeated activity exhaustion, any non-determinism failure, and a persistent open provider circuit without a usable fallback. Human waits, explicit rejection and cancellation are expected states. Hint loss is a degraded-progress notification, not an outage. These are staging targets to validate, not measured production guarantees.
